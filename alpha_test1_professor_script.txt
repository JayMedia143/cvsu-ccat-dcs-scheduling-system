Listen closely as I explain every step of our algorithm using this flowchart. In Box 1, we have the start execution. This is the exact moment we run the code in the terminal to wake up our genetic algorithm engine. In Box 2, we call this the query database phase. Here, our computer reaches out to the database to ask, 'What are all the classes and requirements we need to schedule for this semester?' Moving to Box 3, this is where we load the campus data. We are pulling in all the ingredients for our scheduling recipe, including 87 courses, 43 sections, 29 faculty members, and 17 classrooms. In Box 4, we perform the parse pre-assignments step. This is where we handle the fixed genes—schedules that are already locked and cannot be moved by the AI, such as Saturday NSTP classes or Monday morning Flag Ceremonies. These are firmly set in the system.

Now, let's move into the population initialization phase. In Box 5, we have create genome. Here, we build what we call a population of 100 random schedules. Imagine creating 100 different rough drafts or attempts at organizing the calendar. In Box 6, we make a copy of our fixed genes to ensure that every draft we create still respects those locked-in subjects. In Box 7, we go through every single class that needs to be placed for every section and every course. In Box 8, we check if the class is a lecture or a laboratory. This is important because if it is a lab, the system must ensure it only goes into a computer laboratory. In Box 9, we reach the random placement step. This is the biggest problem in Test 1 because our AI is essentially blindfolded. It picks a random day, a random time, and a random room without checking if someone else is already there. In Box 10, the computer asks, 'Have I finished creating all 100 drafts?' If not, it goes back to Box 6 to keep filling the list.

Now we enter the evaluation and conflict detection phase. In Box 11, we start the evolution loop. This is a repeating cycle designed to gradually improve our schedules. In Box 12, we calculate fitness. This is how we measure how 'good' or 'bad' a schedule is. In Box 13, we encounter the slowest part of our engine, the O-N-squared nested loop scan. The computer compares every single subject against every other subject in the entire campus. This is extremely inefficient, like checking every person's ID in a crowded stadium one by one. In Box 14, we check for the three pillars of collision. We are looking for three specific errors: (1) are two classes in the same room? (2) does a teacher have two classes at the same time? and (3) does a student section have overlapping classes? In Box 15, if a collision is found, we punish that schedule by adding a penalty score. In Box 16, we sum all those penalties to get the total fitness score. In Box 17, we rank all the schedules from the lowest penalty to the highest. Finally, in Box 18, we identify the winner or the best chromosome.

Next is the feasibility check. In Box 19, we ask the critical question: 'Are there zero hard conflicts left?' If the answer is yes, in Boxes 20 and 21, it means we found a perfect schedule and we save it. However, if the answer is no, we must create a new generation of schedules. In Box 22, we use elitism selection to save the top 5 best schedules so we don't lose our progress. In Box 23, we prepare to refill our batch with 95 new schedules. In Box 24, we use the select parents function to pick two existing schedules to 'reproduce' based on their rank. In Box 25, we perform crossover, which combines the genes of the two parents to create a new 'child' schedule. In Boxes 26 and 27, we repeat this crossover until our population pool is full again.

In Box 28, we apply proportional mutate to give the new schedules some slight changes. In Box 29, we ask, 'Does this specific schedule have any conflicts?' If there are no errors, in Box 30, there is still a ten percent chance we will move a subject slightly just to maintain variety and diversity. But if there is an error, we go to Box 31 for blind repair. The AI grabs the subject with the error and throws it into a completely random new day or time. It is a blind guess, so it is a gamble whether it fixes the problem or makes it worse. Finally, in Box 32, we replace the old batch with our new batch and go back to Box 11 for the next generation. As you can see, Test 1 is very slow and relies mostly on luck because our AI is blind when trying to fix those final conflicts.
