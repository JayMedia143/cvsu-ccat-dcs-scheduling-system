Now, let’s discuss the upgrades in our second test case. In Box 1 through Box 4, we follow the same initialization process where we load our data from the database. Because we are still using the Flask query database system, you will notice there is still a significant delay or 'lag' when the program starts up. In our population initialization phase from Box 5 to Box 10, we are still using the standard random placement method. We have not introduced any smart placement strategies yet.

The most critical change is found in the evolution loop. When we reach the step to calculate fitness, we have a brand new technique! Instead of the slow scanning method we used in Test 1, we are now using bitmask caching. Think of this as a master list held in the computer's immediate memory using fast bitwise operations. Instead of the computer having to check every single subject one by one to see if they overlap, it simply glances at its memory list to see if a specific time slot for a room, a teacher, or a section is 'busy' or 'free.' Because of this, the lookup time becomes instant, which is a massive leap in speed!

However, here is the catch: even though we can now detect conflicts incredibly fast thanks to bitmask caching, we are still working on perfecting the repair process. The repair step is still relatively simple and blind, and we don't have the advanced heuristics yet. This Test 2 is all about solving the speed bottleneck of overlap detection!
